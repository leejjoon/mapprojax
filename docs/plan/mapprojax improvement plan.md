# mapprojax improvement plan

Nov 1, 2026 · @이재준 · revised after a two-reviewer committee review (Claude Opus 5.5, Codex gpt-5.6-sol) of the Oct 31 draft

## Where it stands

*Nov 1 snapshot. v0.3.0 shipped on Nov 9 2026; see "Stage 5 closure — Nov 9 2026" at the end. v0.4.0 (`from_astropy`) shipped on Nov 13 2026; see "v0.4.0 closure — Nov 14 2026" at the end. reprojax 0.3.0 shipped on Nov 16 2026. v0.5.0 (ZEA, STG, ARC) shipped on Nov 20 2026; see "v0.5.0 closure — 2026-11-20" in that milestone. Next: reprojax 0.3.1, which widens its cap to `mapprojax[astropy]>=0.5.0,<0.6`.*

mapprojax v0.2.0 is a ~1,200-line WCS core: two projections (TAN, SIN), SIP distortion, NumPy and JAX classes built from shared mixins, PyTree registration, the fp64-free `Reprojector`, and the offset-form `unproj_offset`/`proj_offset` APIs. 89 tests pass. It has no README, no CI, no release, and 0 stars.

The Oct 31 draft overstated two things and missed several bugs:

- **Precision.** "fp64-grade astrometry at fp32 cost" rests on a 200×200 round trip (7.6e-6 px). At realistic image sizes the measured errors are 1.9e-3 px for JAX Mixed and 2.6e-3 px for `Reprojector` f32, up to 8.4e-3 px for a cross-field pair at 0.05″/px (`docs/benchmarks/precision_results.md`). An fp32 pixel coordinate near 4096 has a spacing of 4.9e-4 px, so no fp32 path can reach the round-trip figure in absolute terms. The `reproject.py` docstring (~1e-4 px) and DEVELOPER.md (1e-3 to 1e-2 px) disagree with each other and with the measurements.
- **Correctness.** Four bugs return wrong answers or crash today; see Stage 2. The self-round-trip tests in `tests/test_projections.py` cannot catch them.

## Decisions

1. **mapprojax is JAX-first.** One class per projection, registered as a JAX PyTree. NumPy stays only where fp64 must live on the host: `crval` and the composition of the celestial↔native rotation. The NumPy `Tan`/`Sin` classes, the `*Array` variants (replaced by `vmap`), the `*Mixed` variants (precision becomes a static field, a required keyword) and the private per-projection reprojection legs all go. There is no PyPI release and the only downstream is reprojax, so the API break is cheapest now; no backward-compatibility aliases.
2. **mapprojax is the coordinate kernel; reprojax is the image tool.** mapprojax owns projections, distortions, rotations, precision policy and the source-pixel map with its validity mask. reprojax owns interpolation, flux handling, tiling and coadds. The Oct 31 draft's Phase 4 moves to reprojax.
3. **Compete on the precision design, not on projection count.** jax-galsim `GSFitsWCS` already covers TAN/TPV/TNX/SIP/STG/ZEA/ARC with iterative inversion. mapprojax's distinct contribution is the measured fp32/fp64 envelope, the offset form, and the fp64-free `Reprojector`. Add projections when real data asks for them.
4. **State numbers that survive scrutiny.** Lead with realistic-size errors (~2e-3 px at fp32, ~1e-11 px at fp64) and the plate-scale envelope, not the round-trip figure. Drop "fp64-grade".

## Milestone v0.4.0: `from_astropy`

Nov 12, 2026 · planned by a two-member committee (Fable, Astra) with one reconciliation round; approved by the owner. Not started. mapprojax `main` is at `6d86905` (`0.3.1.dev0`); reprojax 0.2.0 requires `mapprojax>=0.3.0,<0.4`.

The goal: let users and reprojax build a mapprojax kernel straight from an `astropy.wcs.WCS`, with the same refusals as the header loader, and without making astropy a runtime dependency. The release also fixes a SIP parsing defect in the existing header loader.

### Decisions

| | Decision |
| --- | --- |
| **V1** | Release as mapprojax **0.4.0**, then reprojax **0.3.0** requiring `mapprojax>=0.4.0,<0.5`. reprojax's `<0.4` cap has to move anyway, so it moves once. |
| **V2** | Cubes: require a two-axis celestial WCS. Callers pass `wcs.celestial` themselves; the function never drops axes. Automatic extraction can be added later without breaking this contract. |
| **V3** | Frame conversion stays in reprojax. A mapprojax frame helper would be a separate, explicitly approved scope addition. |
| **V4** | astropy is an optional extra, `mapprojax[astropy]`, with `astropy>=7.2.0`. |
| **V5** | `to_header` / `to_astropy` stay deferred. They need their own decisions on frame metadata, pole conventions and lossless versus canonical output. |
| **V6** | The `parse_sip_matrix` fix ships in 0.4.0 as its own commit. |

### API

`mapprojax.from_astropy(wcs, *, precision, inverse_steps=3) -> Tan | Sin`, in a new module `src/mapprojax/astropy.py`, exported lazily from `mapprojax/__init__.py` so that `import mapprojax` never imports astropy. There are no `Tan.from_astropy` / `Sin.from_astropy` classmethods: dispatching on CTYPE avoids a class-mismatch contract.

- **Input:** an `astropy.wcs.WCS` with exactly two pixel and two world axes, longitude first. Not a Header, filename, low-level WCS API object or GWCS.
- **`precision`:** required, with the existing `"f32"` / `"mixed"` / `"f64"` meaning (`wcs.py:119`). It never enables JAX x64. In `"f32"` absolute `proj`/`unproj` are still unavailable; the manual points to the offset methods and `Reprojector`.
- **`inverse_steps`:** passed to the SIP Newton inverse; the default stays `DEFAULT_INVERSE_STEPS` (`sip.py:9`).
- **Output:** an ordinary `Tan` or `Sin` in the input WCS's own celestial frame. RADESYS, EQUINOX, MJD and observation keywords are ignored, not applied and not kept, and the manual says so: "Conversion preserves the numerical pixel-to-coordinate mapping but not the frame identity or observation metadata; keep the original astropy WCS when composing different frames." `to_dict` / `from_dict` round-trip the result unchanged.
- **Errors:** `TypeError` for a wrong input type; `ImportError` naming `pip install 'mapprojax[astropy]'` when astropy is missing; `ValueError` naming the offending property (for example `effective LONPOLE=0`, `cpdis1 is unsupported`), chaining any astropy exception.

`load_wcs_params_from_header` stays public and keeps its behaviour, apart from the SIP fix below. The manual documents `from_astropy` as the preferred entry point, because astropy normalises CROTA, units and alternate-version cards that the raw loader refuses.

### Conversion rules

1. **Work on a copy.** `copy.deepcopy(wcs)`, then `wcs.wcs.set()` on the copy. The caller's object is never changed, and returned arrays never alias astropy's.
2. **Numbers come from attributes**, never from header text: `wcs.wcs.crval`, `wcs.wcs.crpix - 1` (exactly once), `wcs.pixel_scale_matrix`, and `wcs.sip.a/b/ap/bp`. Attributes keep the header's floats bit for bit; `to_header()` was measured to change a 17-significant-digit CRVAL, which already exceeds the 0.1 µas forward budget. `pixel_scale_matrix` covers CD, PC+CDELT, unequal scales and CROTA with astropy's precedence rules, so mapprojax does not reimplement them. CRVAL stays a host float64 array even for `"f32"`, because `Reprojector` needs it.
3. **Units.** Convert each celestial axis's CRVAL and the matching row of the matrix to degrees from its effective `wcs.wcs.cunit`. This covers `preserve_units=True`, where attributes and the re-serialized header both stay in, for example, arcseconds. Refuse non-angular units. CRPIX and SIP coefficients are in pixels and are not touched. The header passed to `_check_cunit` must describe the converted values, not just relabelled CUNIT cards.
4. **Policy checks reuse the existing helpers** in `wcs_utils.py` (`_parse_ctype`, `_check_lonpole`, `_check_pv`) instead of a second copy of the rules. The effective values come from the initialised copy: LONPOLE (only 180 is accepted, and CRVAL2 = +90 without LONPOLE is refused because WCSLIB resolves it to 0), PV terms (SIN accepts only absent or zero PV2_1/PV2_2), CTYPE with `lng`/`lat`.
5. **Hidden distortions.** For a TPV header astropy reports `ctype == 'RA---TAN'`, `get_pv() == []` and `has_distortion == False`, yet `all_pix2world` applies the distortion (11″ in the committee's probe). `to_header(relax=True)` is the one place the TPV suffix and PV cards reappear, so it is used to find unsupported distortion conventions (TPV, TPD, `-TAB`) and run `_parse_ctype` on the CTYPE strings it reports. Classification never relies on `wcs.wcs.ctype`, `get_pv()` or `has_distortion` alone.
6. **Refused:**
   - `cpdis1`, `cpdis2`, `det2im1`, `det2im2` (any lookup table);
   - TPV, TPD, `-TAB` and other unsupported distortion conventions;
   - an effective LONPOLE other than 180, and CRVAL2 = +90 without LONPOLE;
   - nonzero SIN slant parameters, and other PV or PS parameters;
   - swapped axes (latitude first), rather than silently permuting the matrix rows and SIP polynomials;
   - a WCS that is not two-dimensional, with the message "pass `wcs.celestial`";
   - projection codes other than TAN and SIN;
   - non-finite parameters;
   - a SIP reference pixel that differs from CRPIX (mapprojax has one shared reference pixel);
   - nonzero SIP coefficients outside the triangular order astropy evaluates (`i + j > order`). astropy already zeroes them, so this is a cheap guard against mapprojax's rectangular evaluator activating them;
   - a `-SIP` CTYPE with no SIP object.
7. **Accepted:**
   - RA/DEC, GLON/GLAT and ELON/ELAT pairs;
   - ICRS, FK5 and Galactic labels;
   - SIP coefficients without the `-SIP` suffix, matching what astropy applies;
   - LATPOLE as astropy initialises it;
   - CRVAL2 = −90 with effective LONPOLE 180;
   - alternate WCS versions that the supplied object did not select.
8. **SIP inverse.** A/B are used as given. AP/BP, when present, are only the starting guess for the existing Newton solve (`sip.py:151`). No inverse is fitted.

This converts the semantics of the materialised WCS object, not an audit of the original FITS file: cards astropy has already discarded cannot be recovered or refused.

### SIP fix in the header loader

`parse_sip_matrix` (`wcs_utils.py:113`) reads every `{prefix}_{i}_{j}` with `i, j <= order`. The SIP convention, and astropy, define only `i + j <= order`; astropy zeroes and ignores the rest. A header carrying, for example, `A_2_2` with `A_ORDER = 2` therefore makes `load_wcs_params_from_header` disagree with astropy, and the mapprojax evaluator applies a term astropy does not.

- Read only `i + j <= order`, ignoring higher terms exactly as astropy does, so the loader and astropy agree on the same header.
- Test: a header with a nonzero off-triangle term, compared against `all_pix2world` and `all_world2pix`, plus a check that existing fixtures (all triangular) parse unchanged.
- CHANGELOG: list it under fixes as a behaviour change of the public loader.

### Validation

One new test module, plus the SIP-fix test in `tests/test_wcs_utils.py`. Comparisons use `all_pix2world(..., 0)` and converged `all_world2pix`, measured as angular separation and radial pixel error, not raw longitude differences across the wrap.

- **Corpus:** parametrised over `tests/accuracy_reference.py` `cases()` and the SPHEREx header fixtures, with the existing f64 budgets and per-fixture mixed/f32 caps from `test_astropy_reference.py`. No frozen baseline is loosened.
- **Linear forms:** CD; PC + unequal CDELT with rotation; off-diagonal-only CD; CROTA.
- **Units:** degrees, radians and arcseconds, with `preserve_units` both off and on.
- **Frames:** Galactic and FK5 headers convert and agree with astropy in their own frame.
- **SIP:** A/B only; A/B + AP/BP; missing `-SIP` suffix; mismatched SIP CRPIX (refused); off-triangle coefficient (refused).
- **Poles and edges:** CRVAL2 = ±90 cases, longitude wrap, projection boundaries and validity masks.
- **Equivalence:** for headers the raw loader accepts, `from_astropy(WCS(h))` equals `load_wcs_params_from_header(h)` leaf for leaf.
- **Refusals:** one test per refused case, asserting the message, including TPV hidden behind an apparent TAN, a separable cube passed without `.celestial`, swapped axes and a wrong input type.
- **Behaviour:** the caller's WCS is unchanged and arrays don't alias it; `from_dict(to_dict(...))` round-trips; the result works under `jax.jit` and as a PyTree; `"f32"` with x64 off emits no truncation warnings; `import mapprojax` works and stays quiet without astropy (`test_import_is_quiet_with_x64_off` remains the guard); calling `from_astropy` without astropy raises the `ImportError` above.

### Risks

- **Silently missed distortion:** an astropy-hidden convention other than TPV. Mitigation: the `to_header(relax=True)` audit plus the lookup-table attribute checks, and running the full corpus early.
- **`to_header` drift** between astropy versions. Mitigation: it is used only for classification, and `ci/minimum.txt` / `ci/latest.txt` pin both ends.
- **Unit scaling errors.** Mitigation: per-axis conversion and tests with `preserve_units` on and off.
- **Lost frame context:** users composing kernels from different frames without `frame_rotation`. Mitigation: the manual's warning; reprojax keeps the original WCS for frame handling.
- **Cache bypass in reprojax.** Mitigation: the cache key comes only from validated output.
- **SIP fix behaviour change:** headers with off-triangle terms change results. Mitigation: these headers already disagreed with astropy; the CHANGELOG names the change.

### Formulas

Internal plane coordinates are **radians** (`base.py:331-378`). FITS CD and WCSLIB plane coordinates are degrees. In the native frame (reference point at (1, 0, 0), `projections.py` convention), the angular distance ρ from the reference satisfies cos ρ = x and sin ρ = s = √(y² + z²). The radial functions are those of Calabretta & Greisen (2002). Every projection keeps TAN's direction (y, z)/s; only the radial function changes, so the orientation carries over.

| | R(ρ) | Forward `(X, Y)` | Inverse | Inverse valid |
| --- | --- | --- | --- | --- |
| ZEA | 2 sin(ρ/2) | `(y, z) · √(2 / (1 + x))` | `x = 1 − R²/2`, `(y, z) = (X, Y) · √(1 − R²/4)` | `R ≤ 2` |
| STG | 2 tan(ρ/2) | `(y, z) · 2 / (1 + x)` | `k = 1/(1 + R²/4)`, `x = 2k − 1`, `(y, z) = k (X, Y)` | every finite plane point |
| ARC | ρ | `(y, z) · atan2(s, x) / s` | `x = cos R`, `(y, z) = (X, Y) · sin R / R` | `R ≤ π` |

**Numerical forms (required):**

- **No cancellation in 1 + x.** For x < 0, ZEA and STG compute 1 + x as s² / (1 − x). The drafted direct form, measured in mixed `proj` at 0.01°/px:
  - ZEA: 0.129 px off at ρ = 178° and 98.9 px at 179.9°;
  - STG: 14.6 px off at 178° and 2.3·10⁵ px at 179.9°;
  - the stable form: 2·10⁻³ px for ZEA and 0.12 px for STG at 178°.
- **Forward validity is "not the exact antipode".** It is defined as `x > 0 or s² > finfo(dtype).tiny`, not as `x > −1`. In f32, x rounds to −1 within about 0.014° of the antipode, and that test would wrongly mask the disc.
- **Exact antipode is invalid for all three** (a deliberate choice). The point (−1, 0, 0) has no native longitude. WCSLIB returns an arbitrary limb point for ZEA and ARC and NaN for STG. Points near the antipode still map to the limb. The test feeds native (−1, 0, 0) directly: `proj(π, 0)` gives s² ≈ 1.5·10⁻³², so it never reaches the exact antipode.
- **Limbs are strict analytic bounds:** `R ≤ 2` (ZEA) and `R ≤ π` (ARC), including equality, which matches WCSLIB. Mask comparisons against astropy skip a few-ulp band around each limb, except in dedicated exact-limb tests.
- **ARC has three guarded expressions:**
  - forward `atan2(s, x)/s`, as a series in u² = s²/x², selected on `small & x > 0`. Without `x > 0` the series also fires near the antipode: a point at ρ = π − 5·10⁻⁵ landed beside CRPIX in the prototype;
  - inverse `sin R / R`, as a series in R²;
  - inverse `cos R`, as a series in R², so there is no `sqrt` at R² = 0.

  The prototype's `sqrt` + `sinc` gave NaN `unproj` gradients at CRPIX in f64 and mixed.
- **Series details:**
  - terms through sixth order;
  - dtype-static thresholds, starting from s², R² ≤ 10⁻² (f32) and ≤ 10⁻⁴ (f64);
  - the sixth-order truncation error at those thresholds is about 10⁻⁹ relative in f32 and 10⁻¹⁷ in f64;
  - the unselected branch is fed positive finite stand-ins (double `where`), because the outer `where` alone does not protect the pullback.
- **Why this is not a corner case.** Every invalid sample is replaced by native (1, 0, 0) or plane (0, 0) (`base.py:323,329,363,374`), which is exactly ARC's singular point. Every masked sample therefore goes through the series branch, not only CRPIX.
- **Typed constants throughout.** An untyped `1.0` in a `where` put an f64 convert into the f32 `Reprojector` jaxpr in the prototype.
- **STG inverse overflow.** The `k` form keeps the value finite where `(4 − R²)/(4 + R²)` gives inf/inf. It still forms R² = inf above about 1.8·10¹⁹ rad in f32. Keep it only if extreme-finite value and gradient tests pass; otherwise use a scaled, reciprocal-radius form.
- **ZEA at R = 2** is value-valid, but the inverse derivative is singular there. Gradients are required to be finite just inside the limb, not at it, mirroring `test_pixel_map.py:78` and `test_wcs_regressions.py:492` for SIN.

*Feasibility probe (2026-11-20, scratch, not committed):* the drafted formulas, in f64, were re-run by the committee with great-circle separation, 20,000 samples per case, CRVAL2 ∈ {30°, −89°, +90° with LONPOLE = 180}, and pixels reaching plane radii well beyond both limbs. The maximum error against astropy's `all_pix2world` was 3.2·10⁻⁶ mas for ZEA and 4.7·10⁻⁷ mas for ARC and STG, with zero mask mismatches away from the exact antipode. (The original probe checked latitude only.)

## Cut or deferred

- **Image resampling in mapprojax** (`reproject_interp`, flux-conserving variant, tiling, coadd): belongs in reprojax. When it is built there, note that JAX `map_coordinates` supports only order 0 and 1, and that Jacobian-scaled interpolation is not flux-conserving under downsampling (use adaptive anti-aliasing or drizzle).
- **Array-API backend inference and PyTorch/CuPy support**: works against the host-fp64 / device-fp32 split; dfreproject already serves PyTorch users.
- **equinox / flax**: explicit PyTree registration covers the need without a dependency.
- **CAR, AIT, MOL**: needed only for all-sky maps, an audience not targeted yet.
- **AZP, SZP, ZPN, AIR** (the parametrised zenithals): each needs PV parameters and its own domain rules; Milestone v0.5.0 kept to the parameter-free ZEA, STG and ARC. Add when a dataset needs them.
- **Non-default LONPOLE**: the default is already encoded for zenithal projections and is what the SPHEREx template uses (`LONPOLE` 180 at δ₀ = 0.48°). Until then, refuse any effective `LONPOLE` other than 180 (Stage 2); `LATPOLE` has no effect for zenithal projections and is accepted. General support must reproduce WCSLIB's defaults and ambiguity rules, not just a three-angle rotation.
- **`-TAB`, D2IM lookup distortions**: defer unless a user asks.

### Requested changes

**1. Promote SIP Horner evaluation from "Cut or deferred" to Stage 2.** The gradient

| Order-4 SIP, 1201×1201 (real frame size) | ms |
| --- | --- |
| polynomial, broadcast (current) | 498 |
| polynomial, Horner | 8.4 |
| `native_to_pix`, no SIP | 13.7 |

the kernel's usefulness — it is the kernel. Max deviation between the two forms is 5e-7.

see the error and returns `nan` silently. Same code, two behaviours. One test line.

#### The bare-`TanJax` case the item 8 wording misses

With x64 off, `TanJax` is 85.75 mas off on an *ordinary* field (vs 2.3e-7 mas with x64 on) and
100 mas on the L2 header. The cause is `WCSBase.__init__`'s `dtype=float`: it asks for f64,
gets f32, and the celestial↔native rotation is the one step that needs f64 — so this is the
precision design's central claim failing silently. The constructor accepts an f32 request but
silently substitutes an *insufficient* precision, which is worse than either an error or
honest f32. Item 8 covers `Reprojector(f64)` and explicit Mixed constructors; it should also
cover plain `TanJax`/`SinJax` under x64 off: either raise, or keep f32 and document the
envelope. The recommendation is to raise on bare JAX classes too, since their contract today
(rotation in f64) cannot be met — and to let `Reprojector` remain the documented f32 path.

#### Two corrections to the SIP inverse item

Both come from running the plan's own algorithm on the plan's own grids. The acceptance target
(1e-6 px, `tests/accuracy_reference.py`) drives the step budget, so this matters.

**Default step count 3 is one short.** With an AP/BP seed, Newton converges as 2.0e-2, 5.1e-4,
1.3e-5, 3.4e-7, 8.6e-9, 2.2e-10 px (steps 1–6) on the full 2040² L2 detector. Three steps miss
1e-6 by 13×; **four steps pass at 3.4e-7 and the real pair at 5.1e-8**. Set the default to 5,
which keeps a 100× margin (8.6e-9 and 1.1e-9) for 1.5 ms extra at 1201².

**The identity seed needs 6–8 steps.** With A/B and no AP/BP, converging from `(U, V)` gives
33, 0.84, 2.4e-2, 6.1e-4, 1.6e-5, 4.0e-7 px — so four steps land at 6e-4, which the 1e-6 target
rejects on a full detector (the A/B-only regression case is a 100 px field and passes early).
Seed instead from the linearised one-step `(U - f(U, V), V - g(U, V))`: 0.54, 1.1e-2, 2.7e-4,
7.0e-6, 1.8e-7 px, i.e. it reaches budget by step 5. Seed order: AP/BP if present, else the
linearised A/B one-step, never the identity.

**Cost is not a constraint.** A full inverse costs 4.5 ms at 1201² (3 steps) and 8.4 ms (6
steps) under `jit`; one forward polynomial is 0.21 ms. The extra steps are affordable.

**One prototype number does not reproduce as stated.** "Two Newton steps give 3.1e-11 px on the
L2 inverse" is 5.1e-4 px on the 33 × 33 full-detector grid, and 4.0e-5 px on a ±16 px patch.
The step counts above come from `accuracy_reference.py`'s own sampling, so use those.

**The pair is f32-limited, not step-limited.** Forward f32 is 2.4e-4 px from step 3 onward and
does not improve with more steps; the regenerated cap is ~2.9e-4, so the margin is 1.2×, not
10×. Do not tighten the f32 cap later without new evidence.
